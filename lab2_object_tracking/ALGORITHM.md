# ЛР2. Алгоритм трекинга по ключевым точкам: подробно и просто

## 0. Идея в одной картинке

```
кадр 0 (эталон) ──► ORB-точки эталона (запоминаем один раз)
                                   │
каждый новый кадр:                 ▼
  ┌─ резкий? ──нет──► HELD: показываем последнюю рамку (≤ 20 кадров)
  │      да
  ├─ 1. ПОТОК: двигаем точки прошлого кадра (Лукас–Канаде) → H → рамка        (быстро, ~4 мс)
  ├─ 2. ПОИСК: если потока нет / раз в 30 кадров / мало точек:
  │        ORB кадра ↔ ORB эталона → тест Лоу → RANSAC → H → рамка             (медленно, ~30 мс)
  └─ 3. проверка «похоже ли внутри рамки на эталон» (NCC) → принять / потерять
```

Рамка = 4 угла эталона (его ROI), перенесённые гомографией **H** в текущий кадр.

---

## 1. Ключевые точки и дескрипторы ORB

**Ключевая точка** — место, которое легко узнать снова (угол, пятно). **Дескриптор** — «отпечаток» окрестности точки.

**1.1 FAST (поиск углов).** Берём пиксель `p` с яркостью `I(p)` и 16 пикселей на окружности радиуса 3. Точка — угол, если подряд ≥ 9 пикселей окружности **все ярче** `I(p)+t` или **все темнее** `I(p)−t` (t — порог). Это очень дёшево: только сравнения.

**1.2 Пирамида масштабов.** Картинка уменьшается в `scale_factor = 1.2` раза `nlevels = 8` раз, FAST ищет на каждом уровне. Поэтому точка находится и когда объект стал меньше/больше.

**1.3 Ориентация (угол поворота точки).** Чтобы дескриптор не зависел от поворота, в патче вокруг точки считаем моменты:

```
m10 = Σ x·I(x,y),  m01 = Σ y·I(x,y),  m00 = Σ I(x,y)
центроид C = (m10/m00, m01/m00),   θ = atan2(m01, m10)
```
Простыми словами: «куда сдвинут центр яркости» — это направление точки. Патч поворачивается на θ перед описанием.

**1.3 rBRIEF-дескриптор.** 256 пар пикселей в патче (после поворота на θ). Для каждой пары бит:

```
bit_i = 1, если I(a_i) < I(b_i), иначе 0
```
Итого 256 бит = 32 байта.

**1.4 Расстояние — Хэмминг.** Сколько бит различается:

```
d(A,B) = popcount(A XOR B)       // 0…256, чем меньше — тем похожее
```

## 2. Сопоставление и тест Лоу

Для каждого дескриптора кадра ищем два ближайших дескриптора эталона: `d1 ≤ d2`. Совпадение принимаем, только если оно **однозначно лучше** второго:

```
d1 < ratio · d2          (ratio = 0.75; рядом с прошлой позицией мягче — 0.85)
```
Смысл: если лучший и второй по качеству почти одинаковы, точка «похожа на всё» (повторяющаяся текстура) — ей нельзя верить.

**Несколько масштабов эталона.** Эталон хранится в 4 копиях (×1.0, 0.7, 0.5, 0.35), у каждой свои ORB-точки. Когда объект на кадре сильно меньше, чем на кадре 0 (камера отъехала), совпадает копия подходящего масштаба. Все точки пересчитываются в координаты **первого кадра** (`ref_pt = kp / scale`), чтобы всё вело к одной гомографии.

## 3. Гомография и RANSAC

Плоский объект при любом движении камеры переходит в кадр проективным преобразованием — **гомографией** (матрица 3×3, 8 степеней свободы):

```
        ⎡ x' ⎤   ⎡h11 h12 h13⎤ ⎡x⎤                x' = (h11·x + h12·y + h13) / (h31·x + h32·y + h33)
   λ ·  ⎢ y' ⎥ = ⎢h21 h22 h23⎥ ⎢y⎥     ⇒         y' = (h21·x + h22·y + h23) / (h31·x + h32·y + h33)
        ⎣ 1  ⎦   ⎣h31 h32 h33⎦ ⎣1⎦
```
Покрывает сдвиг, поворот, масштаб, наклон (перспективу).

Одной пары точек мало: нужно 4 пары (8 уравнений на 8 неизвестных). Но среди совпадений есть **выбросы** (ложные пары). Поэтому **RANSAC**:

```
повторить много раз:
    взять 4 случайные пары → посчитать H
    inlier = пара, у которой ошибка репроекции  ‖ H·x_ref − x_cur ‖ < ransac_thr (3 px)
запомнить H с наибольшим числом inlier-ов; пересчитать H по всем inlier-ам (МНК)
```
Если inlier-ов < `min_inliers` (12) — объекта нет.

**Рамка:** `quad = H · [TL, TR, BR, BL эталона]` (`perspectiveTransform`). Проверка `plausible_quad`: выпуклый, площадь разумная, не вырожден.

## 4. Оптический поток Лукаса–Канаде (кадр → кадр)

Предположение: яркость точки при движении не меняется. Если точка сдвинулась на `(u,v)` между кадрами:

```
I(x+u, y+v, t+1) = I(x, y, t)    ⇒ (разложение Тейлора)    Ix·u + Iy·v = −It
```
(`Ix, Iy` — градиенты изображения, `It` — разница кадров). Одно уравнение на две неизвестных; LK берёт **окно** (например 21×21), где все пиксели движутся одинаково, и решает МНК:

```
⎡ ΣIx²    ΣIxIy ⎤ ⎡u⎤     ⎡ −ΣIxIt ⎤
⎣ ΣIxIy   ΣIy²  ⎦ ⎣v⎦  =  ⎣ −ΣIyIt ⎦
```
Матрица слева обратима только в угловых точках (потому и следим именно за углами). **Пирамида:** сдвиг ищется сначала на уменьшенной картинке (грубо), потом уточняется на полной — так ловятся большие движения.

**Прямо-обратная проверка (FB).** Двигаем точку вперёд (кадр t → t+1), потом назад (t+1 → t). Вернулись не туда, откуда вышли дальше `fb_thr = 1.5 px` — точка потеряна:

```
‖ x_t − LK_back(LK_fwd(x_t)) ‖ > 1.5  ⇒ выкинуть
```
Затем по выжившим точкам тот же RANSAC строит гомографию.

**Борьба с дрейфом.** Для каждой отслеживаемой точки хранится её координата **в эталоне** (`ref_pts_`). Гомография всегда считается «эталон → кадр» по этим парам, а не цепочкой «кадр→кадр→кадр», поэтому ошибки не накапливаются.

**Пополнение.** Точек стало меньше `flow_points` (150) — `goodFeaturesToTrack` (углы Ши–Томаси) добавляет новые внутри рамки; их координаты в эталоне получаются через `H⁻¹`.

## 5. Проверка по внешнему виду (NCC)

Защита от «поток уехал на фон». Участок кадра внутри рамки «выпрямляется» (`warpPerspective`) в 32×32 и сравнивается с эталонным участком:

```
NCC = Σ (a − ā)(b − b̄) / sqrt( Σ(a − ā)² · Σ(b − b̄)² )     ∈ [−1; 1]
```
Это корреляция, не зависящая от яркости и контраста. Ниже `min_ncc` (0.35; для ORB-кандидата — половина) — результат отвергается.

## 6. Размытие и временная потеря

**Резкость** — дисперсия лапласиана:

```
Δ I = ∂²I/∂x² + ∂²I/∂y²,    sharpness = Var(Δ I)
```
Размытие убирает перепады → лапласиан почти нулевой → дисперсия падает в десятки раз. Считаем в области вокруг прошлой рамки, предварительно **приведя её к ширине 128 px и сглаживая σ=1** (иначе зависело бы от масштаба объекта и шума).

Кадр считается размытым, если `sharpness < blur_ratio · EMA`, где `EMA` — скользящее среднее резкости по удачным кадрам (`0.8·EMA + 0.2·s`), `blur_ratio = 0.35`.

На размытом кадре **ничего не обновляется** (ни точки, ни опорный кадр), показывается последняя рамка (жёлтая, режим Held). Поток потом считается от последнего **чёткого** кадра. Первый чёткий кадр после потери всегда проходит ORB-поиск (не доверяем потоку после разрыва). Держим не дольше `max_hold = 20` кадров, потом — «объект потерян».

## 7. Машина состояний и итог для кадра

| Режим | Когда | Цвет рамки |
|---|---|---|
| **Orb** | найден поиском по эталону | зелёный |
| **Flow** | найден потоком | голубой |
| **Held** | кадр размыт / объект пропал, ≤ 20 кадров | жёлтый |
| **Lost** | нет объекта | рамки нет |

Порядок на кадре: размыт? → Held. Иначе поток. Затем ORB-поиск, если режим ≠ Flow, или прошлый кадр был потерян, или прошло 30 кадров, или inlier-ов потока < 25. ORB-результат берётся вместо потока, если он перекрывает его рамку (IoU > 0.5) или у него больше inlier-ов. Поиск идёт сначала у прошлой рамки (маска, мягкий ratio), потом по всему кадру (строгий ratio).

**Метрика качества (синтетика, где известна истинная рамка):**

```
IoU = площадь(A ∩ B) / площадь(A ∪ B),   считается растрово
```

## 8. Можно ли ускорить SIMD-ом?

Где тратится время (один кадр 960×540, оценка): ORB detect+describe ~60–70 % поиска, match (BF) ~20 %, RANSAC ~5 %, поток ~4 мс. В установившемся режиме работает только поток (~4 мс), поиск — раз в 30 кадров.

| Кандидат | Выгода | Комментарий |
|---|---|---|
| **Хэмминг-матчинг** (`popcount(A^B)` 256 бит) | средняя | NEON: `veorq_u8` → `vcntq_u8` → `vaddvq_u8`; 2 вектора по 16 байт на пару. OpenCV `BFMatcher` уже использует SIMD (на ARM — NEON), выигрыш над ним малозначим |
| **Лапласиан / NCC / resize** (резкость, проверка) | малая | это уже оптимизированные функции OpenCV; наши объёмы малы (128×~100 px) |
| **FAST / ORB-дескриптор** | высокая теоретически | OpenCV уже содержит SIMD; переписывать самим — большой объём работы ради малого выигрыша |
| **LK-поток** | высокая | основное время установившегося режима; в OpenCV оптимизирован, лучшее ускорение — **меньше точек** (`flow_points`) и **меньше окно** |
| **Алгоритмические приёмы** | **самая высокая** | поиск только в области прошлой рамки (меньше кандидатов), меньше кадра (width), `nfeatures`, LSH/FLANN вместо перебора, многопоточность (шаблоны разных масштабов — параллельно) |

Вывод: честно SIMD-ускорять имеет смысл **матчинг Хэмминга** (простая изолированная функция, хорошо ложится на NEON, как в ЛР1) — но конкурировать придётся с уже векторизованным BFMatcher, поэтому ожидайте небольшой выигрыш (оценка: до ~1.5× на стадии match; не измерено). Главный рычаг скорости — алгоритмический: ограничивать область поиска и количество точек.
